## Requirements

- An Apple silicon Mac with Xcode.
- Node 24 or newer, with Corepack.
- Rust and Cargo from [rustup.rs](https://rustup.rs), for the source install below.
- `pnpm` on `PATH`; with Corepack, `corepack enable pnpm` provides it.
- An Expo app that uses `expo-dev-client` and pnpm, with a `pnpm-lock.yaml`.

Setup prepares an iOS simulator. To check on a booted Android emulator instead, see
[Check a plan](../check/).

## Install

No QaReN release has been published yet, so the plugin carries no `qaren` build to download.
Install from a `develop` checkout of the
[repository](https://github.com/Lykhoyda/rn-dev-agent/tree/develop):

<Steps>

1. Clone the checkout and install `qaren` from it:

   ```sh
   git clone --branch develop https://github.com/Lykhoyda/rn-dev-agent.git qaren-src
   cd qaren-src
   bash scripts/install-qaren-from-source.sh
   ```

   The installer builds the runtime tarball, verifies it against a manifest it writes for
   that build, and unpacks it under `~/.qaren/runtime/<version>/`. It prints the installed
   binary path.

2. From your app's root directory, start Claude Code with the checkout's plugin:

   ```sh
   claude --plugin-dir <checkout>/packages/qaren-plugin
   ```

   `<checkout>` is the absolute path of `qaren-src`.

3. Run the setup skill:

   ```text
   /qaren:setup
   ```

</Steps>

### Where `qaren` lands on PATH

The installer links `qaren` into a directory on your `PATH`:

1. The first of `~/.local/bin`, `~/bin`, `/opt/homebrew/bin` and `/usr/local/bin` that is
   on `PATH`, exists and is writable. An earlier IDE or toolchain directory is passed over.
2. Otherwise, the first writable absolute directory on `PATH`. Empty and relative entries
   are skipped.
3. Otherwise, it links `~/.local/bin/qaren` and prints the line to run:

   ```sh
   export PATH="$HOME/.local/bin:$PATH"
   ```

It never edits shell startup files. It replaces only a link it made into
`~/.qaren/runtime/`; any other `qaren` file in that directory is left alone with a notice.
A link problem never fails the install: run `qaren` by the binary path the installer
printed. If an earlier `PATH` directory already holds another `qaren`, that one still runs:
check `command -v qaren`, and use the printed path when it differs. Re-run the installer to
recover an interrupted install.

## What `/qaren:setup` does

Before setup effects, the skill reads the assignment and optional app-root
`.qaren/QA.md` through the shared [Project QA workflow](https://github.com/Lykhoyda/rn-dev-agent/blob/develop/packages/qaren-plugin/skills/using-qaren/references/project-qa.md).
The guide can hold owner-reviewed environment, private procedure references and
coverage instructions; credentials stay outside it. An absent guide does not
block setup. Bare CLI commands do not load it automatically.

Setup runs six steps from the selected app package root. It uses already assigned
routine setup authority and resolves genuine missing facts or custody boundaries.
When a step stops, it names the affected work and fix while independent coverage
continues.

1. **CLI.** It finds the `qaren` binary the plugin verifies. Until a release is published
   it accepts the `qaren` on `PATH` when that binary lives under `~/.qaren/runtime/` and
   its version matches the plugin's. Otherwise it gives you the source install line above
   and offers to run it for you.
2. **App.** It checks that `package.json` lists `expo` and `expo-dev-client` and that
   `pnpm-lock.yaml` exists. It runs `pnpm install` when dependencies are absent and
   installation is within assigned setup authority; otherwise it asks. It reads
   the bundle identifier and app's `slug` from `pnpm exec expo config`; if that
   fails, it uses established assignment facts or resolves only missing values.
3. **Config.** It writes `.qaren/config.yaml`:

   ```yaml
   appId: <bundle identifier>
   devClientScheme: exp+<slug>
   ```

   `exp+<slug>` is the scheme `expo-dev-client` generates. When the app's config turns that
   scheme off, setup uses an established registered scheme or resolves that missing
   value. An existing config
   is compared privately with the detected values and preserved; mismatches need
   resolution, and edits need explicit authority. See [Configuration](../configuration/) for every key.
4. **Device.** It reads the simulator inventory and never boots, shuts down or erases a
   simulator itself. It honors an assigned target first. Otherwise, with one booted
   simulator it passes no device flag. With none, it picks the newest available iPhone and passes `--boot-device --device <udid>`, so
   `qaren` boots it under its device lease. With several and no assigned target, it
   resolves which one to use.
5. **Smoke and ready-route plans.** It reads the app's launch path in source,
   picks a text shown on the first screen, and writes `.qaren/plans/smoke.md`. This plan needs no
   `TYPESAFE_API_KEY`. It also discovers an observable usable main state and the
   real UI route there, including authorized login, onboarding, custom flows and
   loading/animation pages. Existing authenticated state and compatible full plans
   are reused; private login values stay in owner-private plans.
6. **Run.** It starts the first `qaren check` detached, because a cold native build can
   take longer than the host's command limit, and follows the run until it ends. Within a
   minute the progress log names the run, and you can watch it in your own terminal with
   `qaren watch <run-id>`. It then reports the receipt's `result`, `run_id` and
   `next_action`.

A first-screen `pass` proves admission. Setup continues to the observable ready
state and inspects actual saved/not-saved outcomes. A route is called reusable
only after clean replay from a safely obtainable equivalent start and a passing
ready check. Private or unsafe-to-repeat routes can remain recipes with replay
unverified. Smoke, readiness and reuse are reported separately; any already
assigned feature QA continues through every criterion or its explicit evidence
gap. Cleanup follows existing ownership and assigned authority.

## First check

Setup writes the admission smoke plan in this shape, with the text it picked from your first screen:

```md title=".qaren/plans/smoke.md"
## QA

### First screen

1. Wait for "<text>" to appear
✓ "<text>"
```

Run it again yourself from the app's root directory, on the simulator setup used:

```sh
qaren check --plan-file .qaren/plans/smoke.md --device <udid> --json
```

`<udid>` is the simulator setup chose or booted. With exactly one booted simulator you can
leave `--device <udid>` out; with several, `qaren check` refuses without it.

Follow it from a second terminal:

```sh
qaren watch --latest
```

This command checks only the first screen. The skills continue with the ready
route and assigned feature coverage; a smoke pass alone is not feature acceptance.
For another feature, [write a plan](../plans/) or ask `using-qaren` to write one.
